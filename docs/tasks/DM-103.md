# DM-103 · Synthetic CRM Dataset & Reproducible Data Generator

**DONE локально в `dev` · PHASE 1 · 26 ноября 2026 · исходная ревизия Git `25f2f75`.** Следующая задача — DM-104 CRM REST API, READY.

## Цель и реализация

Создан эталон для будущих тестов CRM, продаж и риска с наблюдаемой историей каждого факта. CLI формирует набор в памяти, проверяет бизнес-инварианты, выводит manifest и по явному разрешению вставляет строки в PostgreSQL. Генератор работает на физических моделях DM-102, включая все nullable-колонки, внешние ключи и окно событий.

| Модуль `dealmind.demo` | Ответственность |
| --- | --- |
| `config.py`, `catalog.py`, `scenarios.py` | Pydantic-конфигурация, целые квоты, учебные программы, поведение менеджеров и планы контрольных сделок |
| `dataset.py`, `generator.py` | Неприсоединённые к сессии объекты SQLAlchemy, UUIDv5, локальный Random, история сделки, активности и каноническая сериализация |
| `validator.py`, `manifest.py` | Проверки связей, денег, времени, цепочки и наличия фактов для сценариев. Эталонные суммы, количества и UUID |
| `seeder.py`, `cli.py` | Проверка цели, один commit, сериализация одновременных запусков, повторное чтение, JSON-отчёт и коды завершения |

Пакет использует зависимости существующего backend. Имена и тексты создаются из фиксированных синтетических шаблонов. В описании единственной демоворонки хранится хеш конфигурации. Это позволяет отличить версии набора при равных квотах без добавления таблицы или изменения ревизии `0002`. Приоритет DM-103 в roadmap приведён к P0 из действующего ТЗ. ## Сценарии и валидация

14 CRM-сценариев SYN-001…014 включают заявку, квалификацию, консультацию, предложение, ожидание решения, выигрыш и потерю. Отдельные UUID задают повторное обращение и вторую успешную покупку после закрытия первой, возврат, пропуск, повторный вход, внутреннюю заметку и позднюю запись.

11 SYN-R01…R11 задают факты для открытых сделок с разными сроками касания и follow-up, длительным этапом, новой и старой заявкой без контактов, свежей заметкой после старого контакта, а также закрытую сделку. Девять граничных примеров фиксируют 71/72/73 часа с клиентского контакта, 13/14/15 дней с входа на этап и follow-up за секунду до anchor, в anchor и через секунду после. Валидатор проверяет фактические значения по UUID каждой контрольной сделки. Эти записи можно изучить напрямую через SQL. ## Использование, ограничения и изменённые файлы

Из `apps/api` выполните `uv run --locked python -m dealmind.demo.cli generate --dry-run`. Для подготовленной выделенной базы используйте `uv run --locked python -m dealmind.demo.cli seed --apply`. Повторите ту же команду для проверки идемпотентности. Файл можно прочитать командой `uv run --locked python -m json.tool ../../data/demo/dataset-manifest.json`. [Конфигурация среды, аргументы и коды результата](../../data/demo/README.md)

Набор моделирует одну школу и воронку. Распределения, демо-цены и поведенческие профили служат тестам. Проверка версии допускает ревизию 0002. Новая конфигурация в занятом namespace вызывает конфликт. Сервисы переходов, API, аналитика, скоринг и рекомендации остаются в roadmap. Тестовая загрузка живёт в одноразовой БД. После прогонов тестовый контейнер возвращён в исходное остановленное состояние с сохранением тома. У четырёх контейнеров основного стенда статус healthy.
