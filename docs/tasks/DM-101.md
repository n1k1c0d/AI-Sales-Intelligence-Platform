## Domain scenarios

Каждая строка — спецификация будущего теста. Имена A и B обозначают синтетические организации, время сравнивается в UTC. Таблица определяет вход и наблюдаемый исход для БД, сервиса или аналитики.

| ID | Начальные условия и действие | Ожидаемый результат |
| --- | --- | --- |
| DS-001 | Создать открытую сделку у контакта A, с активным менеджером A и активным этапом new_lead в воронке A | Сделка и запись №1 фиксируются вместе. from_stage_id и closed_at пусты, to_stage_id равен текущему этапу |
| DS-002 | Перевести открытую сделку с суммой 12500.00 RUB в won, имея назначенный follow-up | Одна транзакция фиксирует этап, статус, closed_at и строку истории. План очищен, причина пуста. Владелец, цена, валюта и дата закрытия зафиксированы |
| DS-003 | Закрыть открытую сделку в lost с причиной price | Исход lost, причина price, closed_at равен времени перехода. Терминальный этап и история согласованы |
| DS-004 | Закрыть ту же сделку в lost с пустой причиной | Операция отклонена. У сделки исходный открытый этап, история и план сохранены |
| DS-005 | Провести qualified → consultation → qualified | В истории два входа в qualified. Текущий интервал начинается со второго входа |
| DS-006 | Повторно назначить текущий этап с актуальным ожидаемым номером | Успешный no-op. Число записей, номер и время текущего входа сохранены |
| DS-007 | Для won и для lost попытаться перейти на open или сменить финальный исход | Каждая команда отклонена. Нового открытого интервала нет |
| DS-008 | Тот же контакт после покупки обращается за второй программой | Две сделки с разными UUID, отдельными начальными событиями, суммами и исходами |
| DS-009 | Для сделки A передать существующий UUID владельца B | Составной FK отвергает строку. Проверка повторяется для контакта B и автора активности B |
| DS-010 | Выбрать этап другой воронки A при сохранённом pipeline_id | Отклоняются и текущий этап сделки, и попытка записать чужой from/to в её историю |
| DS-011 | В одной школе создать две Deal с одинаковыми source_system и external_id | Вторая отклонена по частичному UNIQUE. Несколько ручных записей с обоими NULL допустимы |
| DS-012 | Сохранить `001` у двух источников A и отдельно повторить пару в школе B и в таблице Contact | Все комбинации допустимы. Заполненная только наполовину пара недопустима |
| DS-013 | Зарегистрировать состоявшийся звонок в 10:00 по сделке без контактов в истории | Activity сохранена, last_activity_at становится 10:00 в той же транзакции |
| DS-014 | В 12:00 добавить внутреннюю note, после неё внутреннюю task | Времена и авторы событий доступны, last_activity_at остаётся 10:00 |
| DS-015 | После контакта в 10:00 зарегистрировать в 13:00 письмо, фактически полученное в 09:00 | У письма occurred_at=09:00 и created_at=13:00, максимум на сделке остаётся 10:00 |
| DS-016 | Для open проверить next_action_at меньше, равен, больше as_of и NULL | Соответственно просрочено, срок наступил, запланировано, отсутствует. Закрытые сделки исключены |
| DS-017 | Сделка вошла в этап 1 июня. Изменить сумму 10 июня. Проверить на 16 июня в тот же час | На этапе 15 суток от changed_at. Изменение updated_at не создаёт нового входа |
| DS-018 | Повторить применённое внешнее событие после следующего перехода | Идентичное событие подтверждает прежний результат. Состав истории и текущий этап сохранены. Изменённое содержание с тем же ключом даёт конфликт |
| DS-019 | Две продажи по 100.00, одна RUB, другая EUR | Две группы по 100.00. Выручка означает стоимость выигранных продаж |
| DS-020 | Деактивировать менеджера A, у которого уже есть сделки, затем попытаться назначить ему новую | Новое назначение отклонено. Существующие сделки и авторство активностей доступны |
| DS-021 | Два автора читают версию 4 и одновременно выбирают разные этапы | Только один фиксирует переход №5. Второй после блокировки видит конфликт версии. Для нового перехода нужна актуальная версия. Равные timestamps упорядочиваются номером |
| DS-022 | При прямой записи присвоить won сделке на этапе типа open, соблюдая остальные строковые условия | FK на сочетание школы, воронки, этапа и типа отвергает запись |

## Фактическая верификация

- Словари сверены с полями исходного ТЗ. Получены восемь UUID PK, 82 поля с типом и обязательностью, включая добавленный pipeline_id истории. Семь прямых ссылок на организации и 11 составных FK сверены с полями дочерних таблиц и ключами родителей.

- Перечень сценариев содержит DS-001…DS-022, матрица охватывает AC-01…AC-36 без пропусков. Проверка относится к проекту модели. В этой задаче новые таблицы и SQL-тесты не создавались.
- Валидатор `python scripts/check_repository.py` прошёл для 175 путей, `git diff --check` прошёл. Изменения затрагивают только Markdown. CI опубликованного коммита DM-012.1 приведён в начале протокола.
