# DM-001 · Project Foundation & Architecture Baseline

PHASE 0 — Project Foundation · P0 Critical · Architecture / Documentation · ТЗ v1.0.

## Objective

Дать следующему разработчику достаточный контекст, чтобы начать DM-002. По документации он должен суметь объяснить ценность DealMind для отдела продаж, пройти от события CRM до согласованного действия, назвать владельцев данных и найти проверяемый критерий для каждой задачи.

## Scope

Изучить существующий Git-репозиторий. Зафиксировать на русском языке концепцию платформы для онлайн-школы, роли, границы MVP, четыре базовых сценария, сущности, риски и ограничения. Описать выбранный стек и архитектуру Modular Monolith + n8n Integration Layer. Составить roadmap PHASE 0–6, обосновать первый ADR и связать документы относительными ссылками.

## Out of Scope

Установка зависимостей, изменение структуры приложений, создание API, моделей, Compose, frontend, workflow, RAG, подключение LLM и настройка CI относятся к последующим задачам. Операции commit, push, git init и изменение remote в DM-001 не входят.

## Implementation Steps

1. Сверить Git-корень, статус, tracked и untracked файлы, существующие Markdown и конфигурации с исходным описанием.
2. Описать сценарии CRM Analytics, High-Risk Deal Detection, Knowledge Base Q&A и AI Recommendation & Approval. Указать пользователя, триггер, вход, обработку, результат и ограничения.
3. Согласовать направления зависимостей, источники данных, интеграционные ключи, требования к доступу, обработке ошибок, трассировке и локальному запуску.
4. Изобразить системный контекст, обработку CRM-события и путь AI-рекомендации. Зафиксировать решение по монолиту, микросервисам и n8n-centric альтернативе.
5. Составить roadmap со стабильными ID, обновить корневой README, проверить комплект и выставить статусы по итогам приёмки.

## Verification

- Из корня Git проверить `git status --short --untracked-files=all`, `git diff --check`, `git diff --stat` и `git diff --cached --stat`. Новые документы проверить по содержимому отдельно, поскольку обычный diff их не включает.
- Открыть README и пройти по относительным ссылкам во всех шести файлах. Проверить обязательные заголовки, заполненность разделов, структуру таблиц, завершение fenced-блоков и отсутствие заглушек.
- Сверить ID и названия с исходным ТЗ, затем проверить зависимости на неизвестные ID и циклы. Ожидаемые размеры этапов — 12, 9, 8, 9, 9, 9 и 10 задач. Ожидаемые итоговые статусы — одна DONE, одна READY и 64 BACKLOG.
- Проверить Mermaid-блоки доступным валидатором. Отдельно проследить направления стрелок, отсутствие записи n8n в доменные таблицы, путь отказа пользователя и проверку backend перед внешней операцией.
- Прочитать изменённые и новые файлы на предмет противоречий, секретов, реальных клиентских данных и обещаний работающих функций. Сопоставить итоговый набор путей с Required Files.

## Definition of Done

Все AC-01…AC-15 проверены, документы связаны между собой, ответственность за запись и согласование однозначна, roadmap задаёт последовательность и измеримые результаты. Для начала DM-002 достаточно этого комплекта и существующего каркаса.

## Result Summary

До работы Git показывал чистую ветку main. В корне был краткий README, а внутри `dealmind/` — исходная спецификация и каталоги с .gitkeep. README обновлён на прежнем месте, пять документов DM-001 размещены в `docs/` от корня Git, пути существующего каркаса сохранены.

Именование ADR уточняет исходный проектный план. В разделе 10.1 мастер-спецификации указано `0001-architecture.md`, а отдельное ТЗ DM-001 требует `0001-modular-monolith.md`. Используется имя из конкретного ТЗ. Параллельная копия решения не нужна. [Исходная спецификация](../../dealmind/docs/MASTER_SPEC.md)

**Итог приёмки — DONE.** Проверены AC-01…AC-15. Имена и ID всех 66 задач сверены с ТЗ. Каждая зависимость ссылается на существующую предшествующую задачу, циклов нет. Статусы в roadmap — DM-001 DONE, DM-002 READY, остальные 64 BACKLOG. Приоритеты и прямые зависимости, для которых ТЗ не задаёт значения, выбраны по техническим предпосылкам приёмки.

Шесть документов обработаны Markdown-парсером PowerShell. Проверены заголовки, таблицы и 31 относительная ссылка. Mermaid успешно разобрал все три схемы и сгенерировал SVG в локальном браузере. Содержательная проверка подтвердила границы записи в БД, отклонение действия и серверную проверку перед вызовом n8n. Проверка пробелов Git, отдельная проверка новых файлов, просмотр содержания и поиск признаков credentials не выявили нарушений. Программные тесты относятся к следующим задачам.
