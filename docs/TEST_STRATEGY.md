# DealMind · Стратегия тестирования

Проверки PHASE 0. Для изменения в `dev` и для pull request в `main` нужны шесть успешных jobs. Проверка в редакторе и локальный прогон помогают найти причину ошибки до отправки. Результат конкретного коммита на GitHub показывает `CI Gate`. [Конфигурация](../.github/workflows/ci.yml) · [Протокол приёмки](tasks/DM-010.md)

Быстрые unit- и HTTP-тесты выполняются без Docker. В интеграционных тестах с БД используются реальные транзакции, затем проверяется состояние независимой читающей сессии. Восстановление подтверждает HTTP-клиент уже запущенного приложения. Контейнерный слой проверяет несколько критических маршрутов целиком. Приёмка PHASE 0 из свежего клона относится к DM-012. Пользовательские end-to-end сценарии появятся с бизнес-функциями.

## Данные, подмены и имена

Имя теста описывает наблюдаемый результат, например `test_recovery_without_app_restart`. Для регрессии сначала воспроизводят дефект, затем проверяют результат через публичный интерфейс. Для случайных ID и времени проверяют формат, порядок и связь с конкретным запросом.

Fixtures используют синтетические значения и независимое состояние. Временные таблицы и БД принадлежат тестовому проекту. Mock допустим для внешнего HTTP, будущего LLM, ошибок транспорта или управляемого таймаута. Для миграций, SQL, импорта n8n и Docker DNS используются настоящие сервисы. Только штатные lockfiles определяют зависимости. CI может восстановить кеш uv по `apps/api/uv.lock` и кеш npm по `apps/web/package-lock.json`. Установка зависимостей остаётся обязательной при попадании и промахе кеша.

## Что считается успешным

JUnit каждого набора должен содержать выполненные тесты без пропусков и ошибок. Для БД дополнительно проверяются имена обязательных сценариев. После `uv build` проверяются модули и `py.typed` в обоих архивах. Для n8n проверяются статус ветки, один итоговый item, HTTP-коды, UUID, execution ID и ошибки. Статус jobs `failed`, `cancelled`, `skipped` или недостающий результат блокируют gate.

Первое измерение покрытия быстрых Python-тестов дало 316/343 строк. Тесты освобождения сессии при таймауте пула и потере соединения подняли показатель до 325/343 (94,75%). Отдельный PostgreSQL-набор проверяет реальный rollback, миграции и восстановление. Порог покрытия на этом этапе не установлен. [Команды backend](../apps/api/README.md)

## Локальный прогон

1. В корне выполните `python scripts/check_repository.py` и `actionlint .github/workflows/ci.yml`.
2. Прогоните быстрый backend и отдельную PostgreSQL suite по инструкции API. [Backend](../apps/api/README.md)
3. Выполните lint, typecheck, Vitest и production build в `apps/web`. [Frontend](../apps/web/README.md)
4. В корне выполните `python scripts/validate_n8n_workflow.py`, `python -m unittest discover -s scripts/tests -v` и `python scripts/ci_stack.py n8n`.
5. Выполните `python scripts/ci_stack.py smoke`. Контейнерные проверки требуют Docker Compose с поддержкой `!override` и Bash с curl. [Команды и отчёты](../scripts/README.md)

## Проверки CRM

`backend-quality` запускает проверку регистрации восьми моделей, конфигурации связей, типов и enum без БД. `database-integration` запускает их через AsyncSession на PostgreSQL и проверяет Decimal, JSONB, смещения времени, повторную покупку, явную загрузку связей, удаление родителей, commit и rollback.

После проверки меток контейнера, тома, порта и идентификатора кластера фикстура создаёт отдельную БД из `template0`. Негативные случаи используют прямой SQL и проверяют имя нарушенного ограничения. Каждый случай изолирован транзакцией. Миграционный тест использует собственную БД, сверяет системные каталоги, единственный head, pgvector после downgrade и вывод `alembic check` после повторного upgrade. Обязательные группы входят в проверку JUnit. [DB-001–055 и MIG-001–011](tasks/DM-102.md) · [Сценарии DM-101](tasks/DM-101.md)

### Детерминированный набор DM-103

Unit-тесты генерируют эталон без соединения с PostgreSQL, сверяют manifest и проверяют реакцию на повреждённые ссылки, суммы, даты, цепочку этапов и ошибку в последнем контакте. Отдельно проверяются повторные покупки и девять временных границ. Для быстрых сценариев используются 80 сделок.

Интеграционный тест на свежей БД ревизии `0002` дважды запускает CLI с 800 сделками и проверяет отдельными SQL-запросами денежные суммы, квоты, связи, историю и итоги активностей. Другие тесты моделируют частичную копию, отредактированную сделку, сбой поздней вставки, ошибку проверки после commit, несовместимую ревизию и два одновременных запуска. Обязательные тесты входят в JUnit-проверку `database-integration`. [Команды воспроизведения](../data/demo/README.md) · [Фактические результаты](tasks/DM-103.md)

Следующие проверки относятся к прикладным операциям. В DM-105 два независимых соединения проверят конкурирующие переходы и отсутствие частичного commit. Аналитика в DM-106 сверяется с ручным эталоном. Для Risk Engine нужны воспроизводимость, граничные баллы, отсутствующие данные и закрытые сделки. Для интеграций n8n — повторы, дубли и неопределённый исход. Для RAG — недостаточный контекст, для LangGraph — отказ в запрещённом действии и восстановление после ошибки. Уровни E2E и AI evaluations появятся вместе с соответствующими компонентами.
