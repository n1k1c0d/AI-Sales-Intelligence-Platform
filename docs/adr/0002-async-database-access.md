# ADR-0002 · Асинхронный доступ к PostgreSQL

**Статус** — принято в DM-007.

## Контекст

Маршрутам FastAPI требуется единая модель владения соединениями и транзакциями. Несколько записей одной бизнес-операции должны фиксироваться вместе. PostgreSQL с pgvector уже используется в локальном окружении.

## Решение и альтернативы

Используем SQLAlchemy 2.x AsyncEngine, Psycopg 3 и Alembic. AsyncSession поддерживает будущие типизированные модели, а SQLAlchemy Core позволяет выполнять запросы до появления доменных таблиц.

| Альтернатива | Причина выбора текущего решения |
| --- | --- |
| Синхронный SQLAlchemy | Потребовал бы выносить блокирующий ввод-вывод из async-маршрутов. |
| Прямой Psycopg | Сохранил бы async SQL, но потребовал бы отдельно организовать маппинг моделей и метаданные миграций. |
| asyncpg | Подходит для async-доступа. Psycopg даёт одному проекту синхронный и асинхронный интерфейсы к PostgreSQL. |
| SQLModel | Публичные Pydantic-контракты и будущая ORM-схема развиваются независимо. Отдельная надстройка сейчас не требуется. |

## Конфигурация и lifecycle

Одна модель Settings для API и Alembic. Пароль — SecretStr. Драйвер получает объект URL. У каждого приложения собственный engine с ограниченным пулом, pre-ping и таймаутами. Сессии создаются на операцию. Shutdown освобождает пул. Число возможных соединений зависит также от числа процессов API.

## Владение транзакцией

Application service определяет атомарную операцию и выполняет commit либо rollback. Репозиторий может делать flush. Dependency отвечает за закрытие сессии. Длительная работа внешнего сервиса и ожидание действий пользователя выполняются вне открытой транзакции.

## Миграции

Alembic CLI использует отдельный async engine с NullPool и общие метаданные Base. Оператор применяет миграции один раз перед обновлением API. Имена ограничений воспроизводимы. В будущих моделях явно задаётся имя check constraint. Baseline при downgrade сохраняет общее расширение vector. В production потребуется отдельно определить права runtime- и migration-ролей.

## Последствия

Пул и сессии поддаются изолированному тестированию, а HTTP readiness отражает способность выполнить SQL. Требуется соблюдать границы event loop и не передавать AsyncSession параллельным задачам. Фактическая актуальность схемы проверяется отдельной командой Alembic. [Руководство backend](../../apps/api/README.md#database-architecture)
