# ADR-0004 · CRM-модель продаж образовательных программ

**Статус** — принято в DM-101, PHASE 1. **Область** — проектирование схемы и будущих команд FastAPI. [Словарь и ограничения](../DATA_MODEL.md) · [Сценарии](../tasks/DM-101.md)

## Контекст

Клиент демо-школы может отложить решение, вернуться на квалификацию, купить курс и позже обратиться за другой программой. Для аналитики требуется сохранить обе возможности продажи, фактическую последовательность этапов и момент последнего состоявшегося контакта. Схема должна отклонять присвоение сделке существующего UUID из чужой организации даже при ошибке вызывающего кода.

## Решение

1. Deal представляет одну возможность продажи, Contact — одного клиента. Восемь сущностей покрывают сделки, участников, воронки, события и историю. Отдельные Lead, Product, Payment и подсистема задач потребуют собственного бизнес-сценария. У ближайшего действия в MVP есть срок на сделке.
2. Organization задаёт область данных. Составные FK проверяют принадлежность контакта, владельца, исполнителя, воронки и этапов. Тип текущего этапа входит в ссылку Deal вместе со status. В историю добавляется pipeline_id, проверяемый относительно сделки и обеих ролей этапа. Так БД может отклонить переход между двумя воронками одной школы.
3. Открытая сделка перемещается между активными открытыми этапами в любом порядке. Закрытие разрешено с любого из них. Won фиксирует продажу и положительную сумму. Lost требует код причины. Обе операции очищают ближайший план. Терминальный исход окончателен. Повторная продажа создаёт новую сделку у прежнего контакта.
4. Движение хранится отдельными фактами DealStageHistory с номером внутри сделки. Сервис блокирует строку сделки и атомарно сохраняет снимок и строку истории. Возвраты сохраняют предыдущие посещения. Повтор того же внешнего перехода распознаётся по организации, источнику и ID события.
5. Для денежных операций используется Decimal и NUMERIC(14,2). Суммы отчёта группируются по валюте. Отчёт о won отражает стоимость продаж. Для денежных поступлений потребовалась бы отдельная модель платежей. Моменты хранятся в UTC, календарный период отчёта определяется IANA-зоной школы.
6. Состоявшееся взаимодействие call/message/email/meeting определяет last_activity_at. Внутренние note/task и назначение срока сохраняют прежнюю дату последнего контакта. Для первой версии истории назначений и цен достаточно текущего владельца/суммы для open и зафиксированных при закрытии значений для won/lost.

## Альтернативы и последствия

| Рассмотренный вариант | Причина выбора |
| --- | --- |
| Одна карточка клиента с текущим состоянием продажи | Теряется отдельный исход повторной покупки, затрудняется определение знаменателя win rate. Выбраны Contact и Deal с отношением 1:N. |
| Один FK по UUID и фильтр организации в API | UUID из двух организаций могут существовать одновременно. Цена составных ссылок — дополнительные полные UQ и один повторяемый ключ в истории. |
| Хранить только текущий этап и updated_at | Редактирование суммы меняет updated_at. Без истории нельзя восстановить возвраты и пропуски. Выбрана последовательная история действительных переходов. |
| Универсальная CRM с переоткрытием, историей всех полей и управлением задачами | Потребовались бы циклы продажи, журналы назначений и платежей, пока отсутствуют потребители с согласованной семантикой. Выигрыш от узкого MVP — проверяемые метрики, цена — ограниченные исторические срезы. |

Этап сделки на прошлую дату восстанавливается из истории. Точный прежний снимок суммы, валюты, владельца и плана открытой сделки требует версий соответствующих полей. Действия менеджера атрибутируются через Activity.actor_id, коммерческий итог — владельцу на момент закрытия. Детали принудительных ограничений остаются в единой матрице модели. [Асинхронные транзакции](0002-async-database-access.md)

## Когда пересматривать

Поводом для нового решения станут отчёт по оплатам/возвратам, межвороночный перенос, исправления исторических переходов, обязательное reopening исходной возможности или подтверждённая потребность восстановить воронку по менеджеру и сумме на произвольную дату. До работы с реальными данными должны быть определены права доступа и политика удаления персональных сведений.
