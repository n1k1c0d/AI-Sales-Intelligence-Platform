# ADR-0003 · Диагностика FastAPI через Next.js

**Статус** — принято в DM-008, 24 ноября 2026 года.

## Контекст

FastAPI публикует отдельные liveness и PostgreSQL-backed readiness. В Docker он доступен по DNS-имени `api`, на машине разработчика — по опубликованному порту. Пользователю нужен единый экран, который можно открыть и во время отказа одного из сервисов.

## Решение

Используем Next.js App Router. Статическая структура страницы рендерится на сервере. Интерактивная панель получает свежий снимок с `GET /api/system/status` на том же origin. Route Handler принимает только GET и вызывает два фиксированных пути. Он читает `API_BASE_URL` и таймаут в runtime, валидирует ответы Zod и возвращает диагностические поля. Для каждого пути сохраняется отдельный ID. `GET /api/health` отвечает только за процесс web.

FastAPI владеет проверкой PostgreSQL, SQL и бизнес-правилами. Новый обработчик агрегирует HTTP-наблюдения для представления. Статусы CRM и разрешения на операции остаются в Python.

## Альтернатива

Прямые browser-to-FastAPI запросы убирают один HTTP-переход. Тогда каждому клиенту нужен доступный с хоста адрес, CORS-настройка для origin страницы и логика обработки обоих контрактов. В локальном Compose выбран единый origin с runtime-конфигурацией на стороне web.

## Последствия

Один образ работает с разными адресами API. Внутренний hostname остаётся серверной настройкой. Диагностический запрос добавляет один сетевой переход и два обращения к API. Опрос запускается при открытии и ручном обновлении. Следующий этап, которому понадобится новый контракт, добавит отдельную операцию и проверку входных данных.
