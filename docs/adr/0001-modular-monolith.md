# ADR-0001 · Use Modular Monolith Architecture with n8n Integration Layer

## Status

Accepted · PHASE 0 · DM-001. Решение определяет архитектуру будущего MVP. [Область продукта](../PROJECT_CONTEXT.md)

## Context

Один разработчик должен воспроизвести демонстрацию онлайн-школы на локальной машине. При разборе одной сделки участвуют история этапов, правило риска, документы и согласование внешнего действия. На первых этапах модели и контракты будут меняться вместе. Независимые циклы выпуска этих частей пока не требуются. Интеграции, напротив, уже имеют собственные точки отказа — повтор webhook, таймаут CRM или недоступный канал уведомлений.

## Decision

Используем monorepo и модульный монолит FastAPI Backend с n8n Integration Layer. Python-модули отвечают за бизнес-смысл операций, доступ и границы транзакций. PostgreSQL хранит доменные данные, согласования и журнал. n8n взаимодействует с backend через API, принимает внешние события и исполняет разрешённые операции. Это оставляет проверку ключа события и запись доменного изменения в одной транзакции, сохраняя отдельное окружение для интеграционных workflow.

Для проверки риска можно вызвать доменную функцию на фиксированном наборе фактов без сети. Для проверки доставки достаточно запустить экспортированный workflow с тестовым событием и сверить результат с журналом backend. Оба сценария используют один согласованный контракт. ## Alternatives Considered

| Подход | Что даёт | Цена выбора для DealMind |
| --- | --- | --- |
| Modular Monolith + n8n | Общая предметная модель, локальные транзакции и тестирование правил Python. Интеграции меняются отдельными workflow. | Границы модулей и контракт с n8n придётся поддерживать явно. Выбран для MVP. |
| Microservices | Независимые развёртывание и масштабирование CRM, риска и AI. | Изменение сделки и публикация события требуют координации сервисов. Появляются сетевые отказы и больше компонентов для локального демо, при этом отдельная нагрузка пока не измерена. |
| n8n-centric architecture | Короткий путь от webhook до прототипа интеграции. | Формулы и проверки доступа окажутся распределены по узлам workflow. Станет сложнее независимо проверить правило, обеспечить единую транзакцию и повторно использовать логику из UI. |

## Consequences

**Преимущества.** Один backend проще запустить, отладить и обновить. Общая транзакция связывает событие и доменное изменение. Обособленные модули позволяют постепенно расширить сценарий от CRM-аналитики до RAG и согласования, сохраняя тесты бизнес-правил отдельно от доставки.

**Издержки.** У backend-модулей единый цикл деплоя. Сбой ресурсоёмкой операции может затронуть обычные запросы. Неконтролируемые импорты или обращение к чужим таблицам увеличат связанность. На ревью проверяются направления зависимостей, владельцы записи и отсутствие бизнес-правил в routes и workflow.

## Revisit Conditions

Пересмотреть решение стоит, если замеры покажут, что индексация мешает целевой задержке CRM API, восстановление после сбоя требует изоляции процесса или у компонента появился устойчивый независимый цикл выпуска. В новом ADR нужно привести наблюдение, сравнить изоляцию внутри текущего развёртывания с выделением сервиса и описать последствия для согласованности данных и локального запуска.
