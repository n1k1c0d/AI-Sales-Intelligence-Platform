# 1. Общая информация о проекте

## 1.1. Название

**DealMind — AI Sales Intelligence & Automation Platform**

Версия проектной спецификации: `1.0`.

Формат: open-source portfolio project / production-oriented MVP.

## 1.2. Концепция

DealMind — платформа для интеллектуального анализа продаж, выявления проблемных сделок, работы с корпоративной базой знаний и автоматизации CRM-процессов.

Система получает структурированные данные о сделках, менеджерах, клиентах и этапах воронки, а также неструктурированные данные: заметки, переписки, регламенты, скрипты продаж и описание продуктов.

На основе этих данных система:

1. Рассчитывает показатели продаж.
2. Обнаруживает потенциально проблемные сделки.
3. Анализирует историю взаимодействий.
4. Находит релевантную информацию в базе знаний через RAG.
5. Формирует обоснованные AI-рекомендации.
6. Передаёт результаты менеджерам и руководителям.
7. Автоматизирует согласованные действия через n8n.
8. Сохраняет историю анализа, рекомендаций и действий.

## 1.3. Предметная область

На первом этапе бизнес-контекст — продажи образовательных продуктов онлайн-школы.

Основные сущности:
- Менеджеры продаж.
- Потенциальные клиенты.
- Сделки.
- Воронки и этапы продаж.
- Задачи и касания.
- Образовательные продукты.
- Скрипты продаж.
- Возражения.
- База знаний компании.
- Рекомендации и уведомления.

Предметная область должна быть реализована таким образом, чтобы в будущем систему можно было адаптировать к другим B2B/B2C-продажам.

## 1.4. Главная бизнес-проблема

Руководители отделов продаж зачастую видят результаты в CRM постфактум, но не всегда понимают, какие конкретно сделки требуют внимания прямо сейчас.

Менеджеры не всегда своевременно обрабатывают возражения, назначают следующие касания или используют актуальную информацию о продукте.

DealMind должен превращать данные CRM в конкретные, проверяемые рекомендации.

## 1.5. Ключевой пользовательский сценарий

1. Менеджер ведёт сделку.
2. Несколько дней клиент не получает следующего контакта.
3. Детерминированный Risk Engine обнаруживает проблему.
4. Система извлекает историю действий по сделке.
5. AI анализирует доступный контекст.
6. RAG получает актуальную информацию о курсе, тарифах, условиях оплаты и скриптах.
7. AI формирует рекомендацию с объяснением и ссылками на источники.
8. Руководитель или менеджер видит рекомендацию в веб-интерфейсе или Telegram.
9. Пользователь подтверждает либо отклоняет предложенное действие.
10. n8n запускает разрешённую автоматизацию.
11. Результат сохраняется в журнале событий.

# 4. Архитектура системы

## 4.1. Общий подход

Использовать модульный монолит с выделенным интеграционным контуром n8n.

Основные блоки:

**1. Frontend**

Отвечает за:
- Отображение CRM-данных.
- Аналитические дашборды.
- Просмотр проблемных сделок.
- Интерфейс AI-рекомендаций.
- Поиск по базе знаний.
- Подтверждение действий.

**2. Backend API**

Отвечает за:
- Обработку HTTP-запросов.
- Валидацию входных данных.
- Контроль доступа.
- Управление бизнес-сущностями.
- Вызов бизнес-сервисов.
- Предоставление данных frontend и n8n.

**3. Domain Services**

Реализуют:
- Расчёт метрик продаж.
- Анализ активности по сделкам.
- Risk scoring.
- Генерацию задач и рекомендаций.
- Управление состоянием действий.

**4. AI Layer**

Реализует:
- Загрузку знаний.
- Индексирование документов.
- Retrieval.
- RAG.
- AI workflows.
- Tool calling.
- Structured recommendations.
- Проверку оснований для рекомендаций.

**5. Automation Layer**

Реализует:
- Получение событий.
- Синхронизацию с CRM.
- Уведомления.
- Запуск процессов по расписанию.
- Передачу подтверждённых действий во внешние системы.

**6. Data Layer**

Отвечает за:
- Хранение CRM-данных.
- Историю событий.
- Документы.
- Embeddings.
- Результаты анализа.
- Историю выполнения автоматизаций.

## 4.2. Разделение ответственности

Критически важное правило:

**Python вычисляет и принимает детерминированные решения. LLM интерпретирует контекст и предлагает объяснения. n8n организует интеграции и автоматизированные действия.**

Примеры:

- Расчёт конверсии — SQL/Python.
- Проверка просроченного касания — Python.
- Расчёт risk score — Python.
- Извлечение подходящих документов — RAG.
- Анализ возражений клиента — LLM.
- Формирование текста сообщения — LLM.
- Доставка уведомления — n8n.
- Запись результата в CRM — backend/integration workflow после разрешения.

Не разрешать AI выполнять произвольные SQL-запросы к базе или самостоятельные CRM-операции без проверок.

## 4.3. Основные потоки данных

**CRM ingestion:**

CRM / Mock CRM → n8n → FastAPI → Validation → Domain Service → PostgreSQL.

**Deal risk analysis:**

PostgreSQL → Risk Engine → Risk Assessment → API → Dashboard / n8n.

**RAG:**

Document → Parser → Chunking → Embedding → pgvector → Retrieval → LLM → Answer with citations.

**AI recommendation:**

Deal Context → Risk Assessment → Retrieval → LangGraph → Structured Recommendation → Human Approval → n8n → External System.

## 4.4. События и идемпотентность

Для входящих интеграционных событий предусмотреть:
- Уникальный event ID.
- Source system.
- External entity ID.
- Timestamp.
- Payload validation.
- Проверку повторной обработки.
- Логирование результата.
- Возможность безопасного retry.

Интеграционные workflows должны учитывать повторную доставку webhook-событий.

## 5.1. Правила организации backend

- API routes не должны содержать сложную бизнес-логику.
- Schemas описывают входные и выходные данные.
- Models описывают структуры хранения.
- Repositories отвечают за запросы к БД.
- Services реализуют прикладные сценарии.
- Analytics отвечает за вычисление KPI.
- Risk содержит правила выявления проблемных сделок.
- AI отвечает за LLM/RAG orchestration.
- Integrations реализуют взаимодействие с внешними системами.
- Core содержит конфигурацию, логирование и общие инфраструктурные компоненты.

Избегать циклических импортов и глобальных объектов со скрытыми побочными эффектами.

## 5.2. Правила организации frontend

- Компоненты интерфейса должны быть переиспользуемыми.
- API-запросы вынести из визуальных компонентов.
- Функции и модели данных типизировать.
- Функциональность группировать по features.
- Не дублировать backend-вычисления во frontend.

## 5.3. Правила организации n8n

Каждый workflow должен:
- Иметь понятное название.
- Решать одну бизнес-задачу.
- Быть экспортированным в JSON без секретов.
- Иметь описание входных и выходных данных.
- Содержать правила обработки ошибок.
- Учитывать повторную доставку событий.
- Быть воспроизводимым после импорта.

Не создавать скрытые зависимости между workflows.

# 6. Модель данных

## 6.1. Основные сущности

Предусмотреть следующую предметную модель.

| Entity | Назначение |
|---|---|
| Organization | Компания, использующая DealMind |
| User | Менеджер или руководитель |
| Pipeline | Воронка продаж |
| PipelineStage | Этап воронки |
| Contact | Потенциальный клиент |
| Deal | Сделка |
| Activity | Коммуникация или действие |
| DealStageHistory | История переходов сделки |
| IntegrationEvent | Входящее внешнее событие |
| KnowledgeDocument | Документ базы знаний |
| KnowledgeChunk | Часть документа и embedding |
| RiskAssessment | Результат расчёта риска |
| AIRecommendation | Рекомендация AI |
| ActionApproval | Согласование действия |
| AutomationRun | Выполнение автоматизации |
| AuditLog | Журнал значимых действий |

## 6.2. Минимальные поля Deal

- id: UUID.
- organization_id: UUID.
- external_id: nullable string.
- source_system: nullable string.
- contact_id: UUID.
- owner_id: UUID.
- pipeline_id: UUID.
- stage_id: UUID.
- title: string.
- amount: Decimal.
- currency: string.
- status: open / won / lost.
- created_at: datetime.
- updated_at: datetime.
- closed_at: nullable datetime.
- next_action_at: nullable datetime.
- last_activity_at: nullable datetime.

## 6.3. Минимальные поля Activity

- id.
- organization_id.
- deal_id.
- actor_id.
- activity_type.
- direction.
- occurred_at.
- summary.
- metadata.

Типы активности могут включать:
- call;
- message;
- email;
- meeting;
- note;
- task.

## 6.4. Минимальные поля RiskAssessment

- id.
- organization_id.
- deal_id.
- score.
- risk_level.
- triggered_rules.
- evidence.
- assessed_at.

## 6.5. Общие правила моделирования

- Первичные ключи UUID.
- Даты хранятся в UTC.
- Денежные значения хранятся как Decimal / NUMERIC.
- Внешние идентификаторы не заменяют внутренние UUID.
- Предусмотреть уникальность идентификаторов в рамках источника и организации.
- Избегать хранения основных бизнес-полей исключительно в JSON.
- Использовать связи и ограничения целостности.
- Для аналитики этапов хранить историю переходов.
- Для значимых операций сохранять audit trail.

На начальном этапе допускается одна демонстрационная организация, но `organization_id` должен присутствовать в данных для последующего расширения.

Полноценную multi-tenant авторизацию не нужно реализовывать до соответствующего этапа.

# 7. Бизнес-логика

## 7.1. Analytics Engine

Система должна в дальнейшем рассчитывать:

- Количество новых сделок.
- Количество активных сделок.
- Количество успешных и проигранных сделок.
- Сумму активного pipeline.
- Выручку по закрытым успешным сделкам.
- Конверсию между этапами.
- Средний чек.
- Среднюю длительность сделки.
- Количество просроченных задач.
- Активность менеджеров.
- Причины потерь.
- Распределение проблемных сделок.

Определения метрик необходимо закрепить в DATA_MODEL.md или отдельном словаре метрик.

Для конверсии этапов учитывать историю переходов и явно фиксировать правила формирования когорт и периодов. Не делить произвольные текущие остатки этапов друг на друга и не называть это полноценной конверсией.

## 7.2. Risk Engine

Первоначальный risk scoring должен строиться на прозрачных правилах, а не на LLM.

Пример будущей базовой системы:

- Нет активности более 72 часов: +35.
- Нет запланированного следующего действия: +25.
- Следующее действие просрочено: +30.
- Сделка находится на одном этапе более 14 дней: +20.

Итоговое значение ограничивается диапазоном 0–100.

Уровни:
- 0–29: low.
- 30–59: medium.
- 60–100: high.

Эти пороги — стартовые гипотезы, которые нужно проверить на демонстрационных сценариях и документировать.

Правила должны учитывать статус и этап сделки. Закрытые сделки не должны получать предупреждения как открытые. Поля с отсутствующими данными должны обрабатываться явно.

Результат расчёта обязан содержать конкретные причины начисления баллов.

В будущем можно добавить ML-модель, но только после получения подходящих размеченных данных и определения метрик качества.

## 7.3. RAG Engine

Планируемый процесс:

1. Загрузка документа.
2. Определение типа и извлечение текста.
3. Нормализация.
4. Разбиение на чанки.
5. Сохранение метаданных.
6. Генерация embeddings.
7. Запись в pgvector.
8. Поиск релевантных чанков.
9. Передача контекста в LLM.
10. Формирование ответа с источниками.

Метаданные чанка должны включать:
- organization_id;
- document_id;
- document_version;
- chunk_index;
- product/category;
- source reference;
- embedding model/version.

Размерность векторного поля должна соответствовать выбранной embedding-модели. Предусмотреть стратегию переиндексации при смене модели.

Ответы должны ссылаться на найденные документы.

Если данных недостаточно, система должна сообщить об этом, а не выдумывать условия тарифа, скидки или информацию о продукте.

Внешние и загруженные документы считать недоверенным содержимым. Не выполнять инструкции, найденные внутри документов.

## 7.4. AI Agent

Использовать LangGraph для сценариев с состоянием, несколькими шагами и подтверждением действий.

Планируемые tools:
- get_deal_details.
- get_deal_activities.
- get_deal_risk.
- search_knowledge_base.
- get_sales_metrics.
- create_action_draft.
- submit_action_for_approval.

Не давать агенту:
- Произвольный доступ к SQL.
- Возможность изменять любые CRM-поля.
- Доступ к чужой организации.
- Возможность отправлять сообщения клиентам без разрешения.
- Возможность самостоятельно менять цены или коммерческие условия.

Действия с внешними эффектами должны проходить обязательную серверную авторизацию и проверку разрешения пользователя.

Рекомендации возвращать в структурированном формате:
- deal_id;
- recommendation_type;
- summary;
- rationale;
- evidence;
- source_references;
- proposed_action;
- limitations;
- requires_approval.

Не выдумывать точную статистическую уверенность модели. Если вводится confidence score, его смысл и способ вычисления должны быть отдельно определены.

# 13. Нефункциональные требования

## 13.1. Maintainability

- Понятная структура.
- Небольшие функции с определённой ответственностью.
- Типизация.
- Контролируемые зависимости.

- Обработка сетевых ошибок.

- Retry с ограничениями.
- Идемпотентность.
- Контролируемое завершение операций.
- Отсутствие молчаливого игнорирования ошибок.

## 13.3. Security

- Secrets только в environment/secret storage.
- Валидация входных данных.
- Ограничение доступа к интеграционным endpoints.
- Контроль операций с внешними эффектами.
- Защита данных организаций.
- Минимизация логирования персональной информации.
- Безопасная работа с документами.
- Никакого публичного deployment демонстрационного API без подходящей аутентификации.

## 13.4. Observability

Постепенно добавить:
- Structured logging.
- Request IDs.
- Correlation IDs.
- Workflow execution IDs.
- AI tracing.
- Ошибки интеграций.
- LLM token/cost tracking.
- Время выполнения операций.

Другой разработчик должен иметь возможность клонировать репозиторий и повторить локальный запуск по README.

- Domain logic тестируется независимо от HTTP.
- AI providers можно подменять mocks.
- Тесты не должны обязательно расходовать платные LLM tokens.
- Integration tests изолированы от production данных.
- Приоритетное покрытие — критические бизнес-правила и интеграционные контракты, а не искусственный показатель процента строк.

# 14. Демонстрационные данные и сценарии

На PHASE 1 разработать воспроизводимый генератор синтетических данных.

Целевой набор:
- Одна организация.
- 5–10 менеджеров.
- 500–1000 сделок.
- Несколько этапов воронки.
- История переходов.
- Активности.
- Просроченные задачи.
- Успешные и проигранные сделки.
- Различные причины потерь.

Обеспечить:
- Seed parameter.
- Фиксируемую опорную дату.
- Повторяемость генерации.
- Отсутствие реальных персональных данных.
- Понятные бизнес-сценарии.
- Идемпотентность повторного запуска загрузчика.

Пример основного демонстрационного сценария:

**High-Risk Deal Detection**

1. В CRM существует открытая сделка.
2. У сделки есть история активности.
3. Последняя коммуникация произошла более 72 часов назад.
4. Следующее действие не запланировано или просрочено.
5. Risk Engine обнаруживает признаки проблемы.
6. API возвращает риск, причины и подтверждающие данные.
7. На последующих этапах AI формирует рекомендацию.
8. n8n доставляет уведомление.
9. Пользователь подтверждает дальнейшее действие.
10. Система записывает результат.

Именно этот сценарий должен в конечном итоге работать end-to-end и быть продемонстрирован в портфолио.

# 16. Engineering Quality Gates

Не считать задачу завершённой только потому, что код написан.

Минимальные условия для соответствующего изменения:

**Backend**
- Код импортируется.
- Типы согласованы.
- Lint проходит.
- Unit tests проходят.
- Integration tests проходят, если они применимы.
- API contract проверен.

**Database**
- Миграция выполняется.
- Изменения схемы документированы.
- Ограничения целостности проверены.
- Повторный запуск не создаёт некорректные данные.

**n8n**
- Workflow импортируется.
- Credentials не зашиты в JSON.
- Успешный сценарий проверен.
- Ошибка внешнего API обрабатывается.
- Повторное выполнение не вызывает нежелательных дублей.

**RAG**
- Документы корректно извлекаются.
- Источники отслеживаются.
- Retrieval проверен на тестовых вопросах.
- Отсутствующие знания не заменяются выдуманным ответом.
- Качество измеряется на зафиксированном наборе кейсов.

**AI Agent**
- Tools ограничены.
- Outputs валидируются.
- Ошибки обрабатываются.
- Действия согласовываются.
- Состояние процесса сохраняется, когда требуется.
- Есть проверяемая трассировка.

**Frontend**
- Typecheck и build проходят.
- Есть loading/error/empty states.
- API-ошибки не ломают интерфейс.
- Основные пользовательские сценарии проверены.
